# SKU 与交易库存重构

## 评估结论

本轮需要重构，两端代码已接入，并于 2026-09-22 部署云端服务至 health-test 测试空间。未部署生产、未自动迁移库存、未发起真实支付。部署范围和前端发行阻塞见 `health-test-SKU部署记录.md`。

原实现存在可复现的结构性问题：

- 后台规格输入失焦重新生成 SKU，会丢失价格、库存、图片。
- 购物车使用规格文本和价格匹配；改价造成重复项，改名造成失效。
- 下单在客户端检查 SKU 数量，却只修改商品级 remain_count，SKU 库存不减少。
- 库存校验与扣减分离，多行相同 SKU 没有合并校验，存在超卖和部分成功风险。
- 支付前增加销量、取消时从客户端恢复总库存；重复取消可能重复恢复。
- 订单金额和优惠依赖客户端，取消未先关闭渠道支付单。

## 现在的模型

SKU 仍存放在商品的 suks / fs_suks 内，不另建分布式库存系统。

- sku_id：持久身份，不随名称、价格、排序变化。新 SKU 随机生成；历史 SKU 初次读取按商品 ID、库存池和原规格生成确定性标识，随后持久保存。
- legacy_specs：历史名称别名，兼容尚未携带 ID 的旧购物车。出现歧义直接拒绝；已被历史身份使用的名称不能分配给新身份。
- spec_value_ids：后台编辑时保持组合身份，标签重命名保留原价格、库存和图片。
- inventory：当前可售数量。普通与秒杀是**独立分配的库存池**，同一件实物不得重复填入两个池。
- remain_count：两个库存池可售数量的汇总，仅用于兼容展示；交易只使用具体 SKU。
- stock_version=1：商品已完成库存核对；订单使用新版事务模型。
- stock_state：reserved → paid / released；paid → refunded（仅确认完成的未发货整单退款）。

下单在同一个数据库事务内：读取服务器商品和优惠 → 合并同 SKU 购买数量 → 预占 SKU → 占用优惠券 → 创建不可重复的支付订单。数据库事务失败时整单回滚。重复 out_trade_no 返回原订单，不重复预占。订单信息保存为购买时快照。

支付渠道调用在事务外。网络超时不自动放库存，因为渠道可能已成功创建支付单；保留待付款订单，允许使用同一单号重试。首次支付方式固定，换渠道需取消重下。

验签支付通知 / 渠道订单查询确认后，事务内确认订单与销量，重复执行不重复计数。取消先查询和关闭支付渠道订单，再原子恢复 SKU 与优惠券；数据库恢复失败可通过已关闭渠道的查询结果重试。

退款采用固定退款单号；仅收到“受理”不恢复库存。微信 v2 列表、微信 v3 / 支付宝规范化返回明确成功且金额匹配后，整单只恢复一次。部分退款、已发货退货不自动入库，需独立售后流程；旧订单保持旧退款行为。

旧未付款订单取消只恢复旧总量和旧销量，绝不增加新 SKU 库存。旧未付款订单不支持继续支付，需先取消后重下。

## 管理端联动

- add/edit 使用 jlg-goods-admin 保存，校验管理员或 GOODS_EDIT 权限。
- 改规格标签保留 ID 和价格库存。SKU 快照过期时拒绝覆盖，保留输入供核对。
- 已保存 SKU 禁止物理删除，停售用库存归零；商品列表改为下架，保留历史订单引用。
- 普通与秒杀库存独立填写；从普通规格复制到秒杀不再复制库存或 SKU ID。
- 编辑旧商品必须确认实际可售库存，且不能有旧的未付款订单。
- 总销量只读。隐藏未开启的秒杀表单，修复权益回显。

商品新增／编辑页的完整 UI 改版现已实现，包括自动缩略图、裁切、共享编辑器、单规格表单、元输入及稀疏保存。详情见管理端 `docs/商品编辑器开发与验收.md`；兼容接口与新 Schema 已部署 health-test，正式网页发行仍受 AppID 成员权限限制。

## 部署与迁移（必须先在测试空间演练）

1. 备份商品、购物车、订单、优惠券及相关 schema；暂停新下单与商品编辑，记录切换时间。不要在不停单状态直接替换模型。
2. 在测试空间部署公共模块 jlg-commerce、jlg-pay-runtime，再部署 jlg-goods-admin、jlg-cart、uni-pay-co、delete-order，上传对应 schema；云函数安装本次新增的本地模块依赖。
3. uni-pay-co 两个工程内容必须一致；用户端为共享服务源。运行 `node scripts/sync-commerce.js` 检查；修改源后使用 `--write` 同步到管理端。不要用旧管理端支付云对象覆盖新版本。
4. 部署新版管理端与用户端，并阻止旧版本客户端继续下单；旧客户端的直接改库存/改订单权限已被移除，不能继续沿用旧下单流程。
5. 先处理旧待付款订单：已支付的向渠道核实并补齐状态，其余确认关单后取消。不要仅凭本地未付款状态强行放库存。
6. 逐商品核对实物、已付款未发货占用量与秒杀分配量，在后台填写真实可售库存并勾选核对确认后保存。历史 suks.inventory 本身不可信，禁止自动标记全部商品已迁移。
7. 未核对商品不能新下单。核对一个、验收一个，再恢复该商品销售。新商品正常保存即使用新版模型。
8. 定时函数每 5 分钟扫描超过 24 小时未付款订单，并核对处理中退款。生产需确认定时触发器已部署、日志有输出；失败订单保留库存并输出 ID/错误，人工核对后重试。
9. 本地测试无法替代云数据库事务隔离、uni-id 权限及支付渠道验收。完成下面测试空间清单后才开放生产。

回滚：停新下单，先处理全部新版 reserved / refund_pending 订单。**不要直接退回客户端扣库存版本**，它不认识新版库存状态。保留新版关单/退款对账服务直到所有在途订单结清；如需恢复库存，按订单快照逐 SKU 对账，不按历史总库存反推。

## 验证

本地：

```sh
node tests/commerce.test.js
node scripts/sync-commerce.js
```

测试包含模型、事务回滚以及实际支付 service 的模拟渠道接线；并发 fixture 使用串行事务模拟，只证明业务规则，生产事务冲突行为必须在测试空间单独验证。

测试空间必测：

- 两个真实请求争抢最后一件；其中一个失败且库存不为负。
- 多商品下单有一个缺货：无订单、无占券、无其他商品扣减。
- 普通和秒杀同商品混合下单，分别扣库存。
- 客户端伪造金额、SKU、数量、用户 ID，以及直接 JQL 修改库存、订单状态、券占用均失败。
- 支付创建超时后同单号重试、重复验签通知、漏通知后主动查询。
- 渠道关单成功后数据库失败，重试能恢复且只恢复一次；支付与关单竞争不双放库存。
- 退款受理/失败/处理中不放库存；确认成功后只恢复一次；核对实际微信/支付宝回包适配。
- 老购物车在改名、改价后仍匹配同一身份；历史订单规格快照不跟随改名。
- 后台编辑期间发生购买，旧快照保存被拒绝；旧订单未清理时不允许启用新库存。

## 约束

一个订单最多 20 行商品、10 个优惠条目；单个库存池最多 200 个 SKU。保留现有会员折扣及优惠券功能，但金额由服务端重算；前端展示金额不同则要求重新确认。零元订单不进入支付链路。

本轮没有建立仓库、批次、跨仓调拨或通用退货入库系统。退款自动恢复只覆盖当前“未发货整单退款”入口。
